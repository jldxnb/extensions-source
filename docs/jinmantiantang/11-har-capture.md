## 17. 抓包调研方法论

### 17.1 为什么需要抓包

对一个**没有公开 API 文档**的站点做扩展开发，唯一可靠的接口契约来源就是**真实请求**。

第三方开源客户端（`JMComic-Crawler-Python`、`qd-today/templates`）的文档**只能作为线索**。本次实践中，它们提供的关键信息有两处是**错的**：

| 第三方文档说 | 实测结果 | 后果 |
| --- | --- | --- |
| 登录成功标志为 HTTP **301** | 实测为 **200** + JSON `{"status":1}` | 若照抄，成功判据完全失效 |
| 未登录会跳转 `/login` | 实测跳 **`/error/album_missing`**（伪装成作品不存在） | 若照抄，失效自愈永远不会触发 |

> **教训：文档是线索，实测是证据。** 结论必须以自己抓到的数据为准。

---

### 17.2 ⚠️ 最大的坑：Chrome 会「清理」HAR

**从 Chrome v130 起，DevTools 导出的 HAR 默认经过「清理」（sanitized）**，会移除：

- `Cookie` 请求头
- `Set-Cookie` 响应头
- `Authorization` 请求头
- （可能还包括）表单字段中输入的文本

**本次首次导出的两个 HAR 中，`set-cookie` 字面出现次数为 0，所有 `cookies` 数组为空。** 一开始我误以为是解析问题，实为浏览器的默认安全行为。

#### 如何导出**未清理**版本

```
1. F12 打开 DevTools
2. 点右上角 ⚙ 设置  →  偏好设置（Preferences）  →  网络（Network）
3. 勾选 「Allow to generate HAR with sensitive data」
   （中文版：「允许生成包含敏感数据的 HAR」）
4. 关闭设置页
5. 在 Network 面板**长按**导出按钮（此时会出现小箭头）
6. 从下拉菜单选择 「Export HAR (with sensitive data)...」
```

> 注意：**默认仍是清理版**，每次导出都必须长按选未清理版。

#### 什么时候需要未清理版

| 调研目标 | 是否需要未清理版 |
| --- | --- |
| 确认登录接口的 URL / 方法 / 字段名 / 状态码 | ❌ **不需要** |
| 确认成功失败判据（响应体） | ❌ 不需要 |
| 确认是否需要 CSRF token | ❌ 不需要 |
| **确认凭证是 Cookie 还是别的** | ⚠️ 有帮助 |
| 确认会话 Cookie 的**名字** | ✅ 需要 |
| 排查「登录了但请求没带凭证」类问题 | ✅ 需要 |

> **本次实践中，清理版已经足够定稿设计**，因为方案依赖宿主的 CookieJar 自动处理，不需要知道 cookie 名。

### 17.3 抓取步骤（桌面浏览器，推荐）

1. **开无痕窗口**（`Ctrl+Shift+N`）—— 必须从目标状态开始，例如抓登录必须从未登录态起
2. **确定域名** —— 多镜像站点必须在**你实际会用的那个域名**上抓（会话凭证往往域绑定）
3. **先访问一次目标页** —— 顺带观察是否触发人机验证
4. `F12` → **Network** 面板
5. **勾选 `Preserve log`（保留日志）** ← **最关键**，不勾的话页面跳转会清空记录
6. 确认录制圆点是**红色**
7. **执行目标动作**（登录 / 访问受限内容 / 点某个按钮）
8. **不要立刻关 DevTools**，继续抓对照组（见 §17.4）
9. 需要文件时：右键 → `Save all as HAR with content`

---

### 17.4 对照组是必需的

**单份 HAR 往往无法得出结论，必须抓对照。**

本次抓了三份，缺一不可：

| 文件 | 作用 | 缺了会怎样 |
| --- | --- | --- |
| `login.har` | 登录全过程 + 登录后访问受限内容 | 不知道正常路径长什么样 |
| `nologin.har` | 未登录访问同一受限内容 | **无法确定失效判据**（本次靠它才发现跳的是 `/error/album_missing` 而非 `/login`） |
| `wrongPassword.har` | 错误密码登录 | **无法确定失败信号**（本次靠它才发现 `status:2` + 可展示的错误文案） |

**通用原则**：**同一个目标 URL，在不同状态下各抓一次**，差异就是答案。

### 17.5 该看哪些字段

按调研目标分类：

#### 要新增接口调用

| 看什么 | 位置 |
| --- | --- |
| 方法 + 完整 URL | General → Request URL / Request Method |
| Content-Type | Request Headers |
| 请求体字段**名** | Payload / 载荷 |
| 必需的自定义头 | Request Headers（如 `X-Requested-With`、`Origin`、`Referer`） |
| 响应体 | Response / 预览（判断成功失败信号） |

#### 要判断是否需要 CSRF

在**首页 HTML** 里搜 `csrf` / `_token` / `authenticity`。同时看登录表单里是否有隐藏字段。

#### 要判断凭证存储方式

| 证据 | 指向 |
| --- | --- |
| 响应体里有 `token` / `sessionId` 等字符串 | 凭证可能在响应体（需手动注入请求头） |
| 响应体只有状态码，没有任何凭证字符串 | 凭证只能由 `Set-Cookie` 下发 → Cookie |
| 页面用了 `localStorage` | 检查存的是不是凭证（也可能是 UI 偏好） |
| 已登录页面出现「登出」链接 | 服务端凭 Cookie 识别用户 |

#### 要判断防护层

| 关键词 | 含义 |
| --- | --- |
| `cf-mitigated: challenge` | Cloudflare 挑战（响应头） |
| `Just a moment` | Cloudflare 挑战页（响应体） |
| `__cf_chl` / `challenge-platform` | CF 挑战脚本引用（**注意**：普通页面也会内嵌，不等于被挑战） |

> **重要区分**：页面上出现 `challenge-platform` 脚本引用**不代表该请求被挑战**。必须找 **403 状态码 + `cf-mitigated: challenge` 响应头** 才算实证。本次实测中，CF 只挑战了 `/media/users/`（头像）与 `/captcha`，**登录接口未被挑战**。

### 17.6 安全：不要把敏感数据交出去

HAR 可能包含账号、密码、会话 Cookie。**优先采用「自己看图回答」，而不是把文件发出去。**

推荐流程：

1. 在 DevTools 里直接查看上述字段
2. **只报告字段名、状态码、结构**，值一律写成 `REDACTED`
3. 确需发送文件时，先按 §17.2 导出**清理版**（默认就是清理版，这已经天然安全）

本次实践中，全部结论均可从**清理版**得出——这也说明**大多数调研根本不需要敏感数据**。

---

### 17.7 分析：不要整份读入

HAR 可能非常大（本次登录版 **60 MB / 609 条目**，含大量响应体）。

**正确做法**：写脚本按需提取，只输出结构化摘要：

- 按 `mimeType` / 扩展名过滤掉静态资源，只看 document、xhr、json
- 只打印状态码、路径、header **名**、表单字段**名**
- 敏感值（cookie、authorization、密码）只输出长度或直接屏蔽
- 打印前先把值用正则替换掉

**反面做法**：把 60 MB 文件整体读入上下文 —— 既浪费又可能泄露数据。

### 17.8 常见坑清单

| 坑 | 后果 | 规避 |
| --- | --- | --- |
| 没勾 `Preserve log` | 跳转后记录被清空，白抓 | 抓之前必勾 |
| 从已登录状态开始抓登录 | 根本不会产生登录请求 | 用无痕窗口 |
| 抓的域名与实际使用的镜像不一致 | 会话凭证域不匹配，结论作废 | 先定域名 |
| 导出选了清理版却要找 Cookie | 找不到，误判为解析错误 | 看 §17.2 |
| 只抓一份，没有对照组 | 无法判断「差异」即失效判据 | 见 §17.4 |
| 把 `challenge-platform` 当成被挑战 | 误判站点有 CF 拦截 | 见 §17.5 |
| 把 HAR 整份读入上下文 | 浪费 + 泄露风险 | 见 §17.6 / §17.7 |
| 忘了 HAR 未入库 | 60 MB 文件混进 git | 本次已加 `.gitignore` 的 `/har/` |
